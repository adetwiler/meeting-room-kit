Meeting room kit

How it works, what it costs, how to set it up

A static web page that hosts a real video meeting. No server to run, no database, no accounts, and no credentials stored in the thing you deploy.

How it works

The page is plain HTML and JavaScript. It connects to LiveKit, an open-source WebRTC platform, using an access token that is created somewhere else and passed in the URL.

Why the token is minted outside the page

Signing a token needs an API secret. If the page did the signing, that secret would have to be shipped to every browser that loads it, which is the same as publishing it.

So mint-token.mjs signs tokens wherever you run it, and the browser only ever receives the finished token: scoped to one room, with an expiry. Three things follow, and they are the whole reason for this shape:

  • The hosted page holds nothing worth stealing. A static host is genuinely sufficient rather than a shortcut.
  • A leaked link expires by itself. It grants one room for a few hours, not an account.
  • There is no server to run, patch, monitor or pay for.

Not included: recording

Deliberately. Recording is where the real questions live: consent, retention, who may read it afterwards, and in any regulated setting whether it may exist at all. That belongs to whoever owns the compliance posture.

If this goes anywhere near regulated or client data, treat recording as the first question rather than a later feature, and check it against your own policies before anyone dials in. The room states "not recorded" in its header on purpose: for anyone evaluating it, the useful signal is the explicit negative, not silence.

Minutes are counted per participant, so a two-person call uses 2 minutes for every minute of wall clock. On the free tier that is roughly:

  • 41 hours a month of one-to-one calls
  • 27 hours with three people
  • 20 hours with four

Overage above the included amounts runs about $0.0005 per participant-minute on Ship. Hosting the page itself is free on any static host: it is one HTML file and a vendored library, well under a megabyte.

One number nobody should assume. LiveKit's pricing page says overage is billed at standard rates on the free Build tier, while their documentation elsewhere describes Build as having no overage allowed. Those statements conflict. It does not matter at pilot volume, but pin it down before anyone depends on it.

LiveKit's server is also open source and self-hostable, so none of this is a one-way door. The page connects to a URL; where that URL points is your decision.

Setting it up

  1. Create a LiveKit project. LiveKit Cloud's free tier needs no card. Note three values: the wss:// project URL, the API key, and the API secret. The secret displays once.
  2. Host the public/ folder on any static host. It needs HTTPS, because browsers refuse camera and microphone access on plain HTTP.
  3. Mint a link per person. Same --room value means the same call; give each person their own --identity so names render. 
    LIVEKIT_URL=wss://your-project.example \
LIVEKIT_API_KEY=... \
LIVEKIT_API_SECRET=... \
node mint-token.mjs --room standup --identity sam --hours 4 \
  --base https://your-room-host
  4. Send each person their own link. Never reuse one link for two people: identity lives in the token, so two people on one link both show up as the same person.

Things that will bite you

  • HTTPS is mandatory. No camera or microphone on plain HTTP, in any browser.
  • Device names are hidden until permission is granted. Before you turn on a mic, the picker can only show generic entries. That is the browser, not the page.
  • Speaker selection does not exist in Safari or Firefox. The row hides itself there rather than offering a control that silently does nothing.
  • Corporate networks. WebRTC needs UDP. Locked-down networks may need firewall rules or a TURN relay; the connection-quality chip is the early warning.
  • Links expire (4 hours by default). An expired link looks exactly like a broken one, so say so when you send it.

Licensing

public/vendor/livekit-client.umd.js is the LiveKit JavaScript client SDK, Apache-2.0, vendored unmodified so the page has no CDN dependency and works offline.

Everything else is a thin wrapper: one HTML page and one token script, plain standard-library code, no dependencies and no proprietary logic. There is deliberately nothing novel or business-specific in it, so it can be adopted, rewritten or thrown away freely.

No analytics, no telemetry, no third-party requests beyond your own LiveKit endpoint.
